1 Executive Summary

Roshetety is a bilingual patient-facing mobile application that enables pharmacy customers to submit prescriptions digitally and track their order fulfillment in real time. It is the consumer-facing frontend of the APMS (Advanced Pharmacy Management System) — a comprehensive pharmacy automation platform that manages inventory, robotic dispensing, invoicing, and AI-powered analytics.

The app bridges the gap between patients and the pharmacy by replacing paper-based prescription drop-offs with a seamless digital workflow. Patients can either type medicine names manually or snap a photo of a paper prescription (OCR-powered extraction), review the results, and submit the order with a single tap. Real-time WebSocket connectivity provides live status updates when the order is ready for pickup.

2 Problem Statement

Traditional pharmacy prescription workflows suffer from several pain points:

  • Paper dependency: Patients must physically bring handwritten prescriptions to the pharmacy and wait in line for processing.
  • No visibility: Once a prescription is dropped off, there is no way for the patient to know when it will be ready — leading to frustration and repeated phone calls.
  • Manual data entry: Pharmacy staff must manually read and enter medicine names, quantities, and dosages — a slow, error-prone process.
  • Language barriers: Prescriptions may be in Arabic or English, and pharmacists must interpret both accurately.
  • Communication gaps: Status updates require staff intervention (phone calls, in-person inquiries), consuming valuable counter time.

Roshetety was designed to solve all of these problems in a single, intuitive mobile experience.

5 Key Features

Bilingual (Arabic/English)

Full RTL support. The app detects device locale and allows manual switching. All UI text, dialogs, and error messages are localized.

OCR Prescription Scanner

Uses an Ollama-based AI OCR service with a two-pass validation engine: fuzzy string matching followed by visual confusion correction for common OCR errors (e.g., rn → m).

Manual Quick Order

Type a medicine name and set quantity with +/- stepper. Sends directly to the APMS backend. Instant order ID generation with zero friction.

Real-Time Order Tracking

Dual-channel approach: initial fetch via HTTP GET, then persistent WebSocket connection for push events. The screen auto-updates when the pharmacy marks the order as ready.

Cross-Platform

Built with Flutter — single codebase deploys to iOS, Android, Web, Windows, macOS, and Linux. Consistent experience everywhere.

Network Resiliency

Graceful degradation when the backend or OCR service is unreachable. Clear user-facing error messages in the active language. Timeout handling at 8 seconds.

Data Flow: Image → OCR → Order

  1. User captures a prescription photo via camera or gallery.
  2. The app sends the image as multipart/form-data to the OCR service.
  3. The OCR service runs the image through glm-ocr:latest (Ollama), extracts raw text, parses candidate medicine names, and validates each against a CSV-loaded medicine database using a two-pass algorithm (fuzzy → visual correction).
  4. Validated medicine names are returned to the app as a JSON array.
  5. The user reviews the extracted list on the Result Screen, optionally correcting any misreads.
  6. On confirmation, the app POSTs to /api/prescriptions with the medicine names as requested_name items.
  7. The APMS backend creates the prescription record, links it to inventory via the medicine_linker_sheet in the staff dashboard, and dispatches the robot arm for automated dispensing.
  8. When the pharmacist marks the prescription as COMPLETE, a WebSocket ORDER_READY event is broadcast to all connected clients.
  9. The patient's tracking screen receives the event and displays a ready-for-pickup notification.

OCR Validation Pipeline

The ocr_core.py engine uses a sophisticated two-pass approach to handle real-world OCR noise:

  • Pass 1 — Fuzzy Matching: For each extracted word, SequenceMatcher compares against a database of ~1,200+ English medicine names at 70% threshold. Prefix matching gives bonus scores for longer completions.
  • Pass 2 — Visual Confusion Correction: If confidence is below 80%, the engine generates OCR variants using a OCR_VISUAL_MAP (e.g., 'rn' → 'm', 'O' → '0', 'cl' → 'd') and re-scores against the top 100 candidates.
  • Validation Gate: Only matches with score ≥ 0.80 or with ≤ 2 character differences at ≥ 0.70 are accepted as valid.

9 Outcomes & Impact

✓ Reduced Wait Times

Patients submit prescriptions before arriving. Staff pre-process orders, reducing in-store wait from minutes to seconds.

✓ Eliminated Data Entry Errors

OCR extraction with validation catches misreads before they reach the pharmacy system. Manual typing is replaced with a review-and-confirm flow.

✓ 24/7 Ordering

Patients can submit prescriptions anytime, even when the pharmacy is closed. Orders queue in the system for next-day processing.

✓ Transparent Communication

Real-time order tracking eliminates phone calls and in-person status inquiries. Patients know exactly when their order is ready.

✓ Bilingual Accessibility

Arabic-first design ensures the app is usable by the majority of the target demographic while remaining fully accessible in English.

✓ Scalable Architecture

Flutter's cross-platform output and the modular Node.js backend allow the system to scale across multiple pharmacy locations with minimal additional overhead.

11 Future Roadmap

  • Barcode/QR scanning: Integration with mobile_scanner (already in pubspec.yaml) for instant patient check-in via loyalty cards or prescription QR codes.
  • On-device ML: Google ML Kit text recognition (already declared in dependencies) for offline OCR capability without server dependency.
  • Push notifications: Replace WebSocket polling with FCM/APNs push for order-ready alerts even when the app is backgrounded.
  • Multi-pharmacy support: Let users select from a list of nearby APMS-enabled pharmacies and route orders accordingly.
  • Prescription history: Display past orders, repeat prescription functionality, and medication refill reminders.
  • Provider state management: Refactor to use provider (already declared) for cleaner separation of concerns and testable business logic.
